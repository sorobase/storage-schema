## The gap

A Soroban contract-data ledger entry is a key `SCVal`, a durability and a value `SCVal`. It carries no name and no type. The callable interface in `contractspecv0` does not help: since soroban-sdk 28, spec shaking removes every type that only appears in storage. So an explorer, an indexer, a wallet or Lab that reads a contract's storage sees `[Symbol("Balance"), Address] -> I128` and has to guess.

The open question in [rs-soroban-sdk#1818](https://github.com/stellar/rs-soroban-sdk/issues/1818) (2026-04-28) is exactly this: *how does an off-chain consumer looking at a contract storage ledger entry determine which contract type in the storage schema should apply?* This project is one concrete answer, with a reference implementation and measurements.

## What it is

- **A format.** A Wasm custom section, `contractstoragev0`, next to `contractspecv0`. It lists the keys a contract writes (exact, tagged or typed patterns), their durability and value types, and carries the type definitions that spec shaking removed. The host never reads it. [Section format](/reference/format/)
- **A rule for mapping entries.** Durability partitions, the most specific pattern wins, and the decoder answers with one of four statuses. It never guesses. [Matching and statuses](/reference/matching/)
- **Tools.** Attribute macros that emit the section (`#[storage_schema]`, `#[storage_key]`, `storage_schema_extern!`), a sidecar JSON for contracts that never adopt them (including the Stellar Asset Contract, which has no wasm), post-build `inject`/`strip`, a lint for key collisions, a decoder, a read-only RPC client, a CLI, and the same decoder compiled to WebAssembly for this site.

The whole change to the soroban-examples token is one attribute per key variant:

```rust
#[storage_schema]
#[derive(Clone)]
#[contracttype]
pub enum DataKey {
    #[storage(temporary, value = AllowanceValue)] Allowance(AllowanceDataKey),
    #[storage(persistent, value = i128)]          Balance(Address),
    #[storage(skip)]                              State(Address),
    #[storage(instance, value = Address)]         Admin,
}
```

After `stellar contract build` (CLI 25.2.0, spec shaking on), that wasm carries {token.contractstoragev0.keys.length} key entries and {token.contractstoragev0.types.length} type definitions ({token.contractstoragev0.types.join(', ')}). Its `contractspecv0` kept {token.contractspecv0.udts.length} user types. The section costs {fmt(tokenPair.contractstoragev0_section_bytes)} bytes, and the code is byte-identical to a build without it <ProvenanceChip kind="fixture" date={size.measured.slice(0, 10)} source="scripts/build-demos.sh" href="/size/" note={size.method} />.

## Why Stellar, and why a separate section

The idea of putting the layout in the deployed artefact comes from the #1818 thread itself: storage types do not belong in the callable spec, and a separate custom section was suggested there. Solidity's `storageLayout` and Anchor's IDL keep layouts beside the build, not in it. A section travels with the wasm hash, so any reader that can fetch a contract's code can find its schema, with no registry. It is informational and opt-in: a contract without it is valid and decodes as `unknown`, and a contract that never adopts the macros can still get a schema post-build or through a sidecar.
